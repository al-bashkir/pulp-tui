## Limitations

* Content Views, environments and their history live in the local SQLite file of one
  operator, or, with `[database]` or the `database` of a profile, in a database that
  several operators share (PostgreSQL, or SQLite on one host). There is no pulp-tui
  server: each pulp-tui connects directly. Other operators' changes show after a refresh.
* Client-orchestrated steps (publish/promote) continue only while pulp-tui runs; Pulp
  tasks always continue. Interrupted publishes resume with *Resume*, also by another
  operator when the database is shared. No daemon resumes them unattended.
* pulp-tui locks one Content View per workflow (expiry 2 minutes, renewal every 30 s, from
  the clients' clocks). Operations on the same repository from other tools, and from two
  databases that manage one Pulp server, are only serialized by Pulp's task resource locks
  (the later task waits; visible in Tasks).
* The **K** key stores the Pulp secret of a profile, and the database password of a profile
  that has its own `database` (keyring user `[database]:<profile>`). The password of the
  top-level `[database]` still cannot be stored with **K**; use `env:` or `file:`, or
  create the keyring entry (service `pulp-tui`, user `[database]`) with the system tool.
* The shared-database TLS path (private CA, non-loopback host) is checked by hand, not by
  `tests/run-live.sh`. `ca_cert` adds to the built-in Mozilla roots; the OS trust store is
  not used (COMPATIBILITY.md).
* Two live TUI sessions on a shared database were not run by hand; the lock logic is
  covered by the unit and live tests.
* The TUI flows of the database per profile (open on Connect, migrate confirm, copy and
  switch on Edit) are covered by unit tests with mock servers and SQLite files, and the
  store and config parts by the live PostgreSQL test. They were not run by hand in a
  terminal.
* The TUI flow of the environment relabel (Edit form, impact list with typed confirmation,
  result view) was not run by hand in a terminal. The service behind it (`relabel_env`) is
  covered by unit tests with a mock server and by `live_cv`; the key classification by a
  unit test.
* Fallback replication synchronizes content only and never deletes.
* The TUI flows of composite Content Views (the Composite flag of Create, Add components
  with the pin form, Edit with pins and auto publish, the auto publish notice, the delete
  confirmations) were not run by hand in a terminal. They are covered by unit tests with
  mock servers and SQLite stores; the service behind them is covered by `live_cv`.
* A composite has no filters of its own and cannot be a component of another composite.
  Reusable filter sets are not implemented.
* Plugins other than RPM, File and Deb, content guard creation, signing service creation,
  OIDC token refresh: not supported.
* Deb is supported for repositories, remotes, content, copy, publish (optional signing
  service), distributions and Content Views (filters, signing choice, resume, composites).
  Not goals: upload of `.deb` files, replication (native or fallback; a Deb distribution is
  skipped with a note), verbatim publications, dependency solving on copy. The signing
  service pickers list the services of all plugins (pulpcore has no type filter); Pulp
  refuses a wrong one. A large selection is sent in batches below Pulp's 2.5 MiB body limit
  (COMPATIBILITY.md). Deb Content View publications are never reused, so each version has its own.
* The TUI flows of Deb (Publish with a signing service, the Deb signing choice of a
  Content View publish) were not run by hand in a terminal. They are covered by unit
  tests; the services behind them by `live_deb`.
* Not tested: Pulp domains, macOS at runtime (CI builds and runs unit tests), Windows.
* `nested_by_digest` RPM layout: served-content checks verify metadata only.

## Risks

* Native replication is a pulpcore technology preview; its API changed between versions
  (for example `policy`, `q_select`). pulp-tui reads the live schema, but older or newer
  servers may need adjustments.
* pulpcore serves files of superseded publications for
  `DISTRIBUTED_PUBLICATION_RETENTION_PERIOD` (default 3 days). After a rollback, clients
  that use repository metadata get the old content immediately; direct file URLs may
  still work during the grace period.
* An RPM filter that excludes a package of a module or a comps group excludes it: the module
  or group then lists a package that the snapshot does not have.
* The derived repository and distribution names are derived from view, environment and
  repository names; renaming a source repository in Pulp does not rename them.
